# 08. AI 기능 연결

## 배경/목적

Phase 1~7에서 "AI 추천은 Phase 8에서 연결"로 미뤄뒀던 3곳(팀장 후보 추천, 팀장 투표 동률 추천,
공모전 카테고리 추천)을 실제로 연결한다.

## 엔티티 · 필드 정의

새 엔티티/컬럼 없음. 기존 `Message.metadata`(JSON 텍스트)에 추천 결과를 실어 카드 메시지로
내려준다.

## 결정사항

- **AI 연동 방식**: 이 프로젝트에는 실제 LLM 연동이 없고 `global/ai/AiClient` 인터페이스 +
  `MockAiClient` 하나뿐이다 (기존 프로젝트 AI 요약 기능과 동일한 패턴). Phase 8도
  같은 패턴을 따라 `AiClient`에 메서드 3개를 추가했다. 처음엔 `MockAiClient`가 셔플/랜덤으로
  응답했지만, **(2026-08-05 갱신)** 팀장 후보 추천 2개(`recommendLeaderCandidates`,
  `recommendTiebreakLeader`)는 PM이 정리한 규칙기반 점수 알고리즘으로 교체됐다 — 더 이상
  랜덤이 아니라 결정론적 계산이다. 자세한 점수식은 [02-leader-election.md](./02-leader-election.md)
  참고. **(2026-08-05 추가 갱신)** `recommendContests`도 셔플에서 규칙기반(마감 최장순
  상위 N개 유지)으로 교체됐다. `answerTeamQuestion`만 여전히 키워드 기반 Mock이다.
  실제 LLM으로 교체하려면 `AiClient`의 새 구현체만 추가하면 되도록 인터페이스 경계를 맞췄다.
- **팀장 후보 AI 2명 추천**: `ChatbotOrchestrationService`가 `OPEN_NOMINATION`(팀장 희망
  "네" 0명) 팀의 `LEADER_NOMINATION_CARD`를 발행할 때 `AiClient.recommendLeaderCandidates`로
  최대 2명을 뽑아 메시지 문구 + 메타데이터(`aiRecommendedTeamMemberIds`)에 포함한다.
  **정보성 표시일 뿐** — 실제 후보 지정(`isPreLeaderCandidate`)이나 투표 로직에는 영향을 주지
  않는다. **(2026-08-05 갱신)** `AUTO_ASSIGNED`(팀장 희망 1명)/`CANDIDATE_VOTE`(2명 이상)
  팀은 이 카드 자체를 발행하지 않는다 — [02-leader-election.md](./02-leader-election.md) 참고.
- **팀장 투표 동률 → AI 추천 수락**: `LeaderElectionService.tally()`의 동률 분기에서
  `AiClient.recommendTiebreakLeader`로 1명을 추천해 `LEADER_VOTE_CARD` 메타데이터에
  `aiRecommendedTeamMemberId`로 포함한다. 신규 API `POST /api/teams/{teamId}/leader-votes/ai-recommendation/accept`
  — 활성 팀원 누구나 호출 가능(선착순 1명이 확정, 이후 팀 상태가 `LEADER_DECIDED`로 바뀌므로 뒤늦은
  다른 팀원의 요청은 자연히 `INVALID_TEAM_STATUS`로 막힘). 서버가 별도 상태를 저장하지 않고
  **가장 최근에 발행된 `LEADER_VOTE_CARD` 메시지의 metadata를 읽어** 추천 후보를 판정한다.
  **(2026-08-05 갱신)** 재투표(2라운드 이상)도 또 동률이면 사용자의 수락 없이 AI 추천으로
  자동 확정한다(무한 재투표 방지).
- **공모전 카테고리 AI 추천**: `ChatbotOrchestrationService.advanceToContestSelecting`이
  `Team.preferredCategory` 기준으로 열려있는(`OPEN`) 공모전을 조회한 뒤 `AiClient.recommendContests`로
  추려 `CONTEST_RECOMMEND_CARD`로 발행한다. 추천 결과가 없으면(카테고리에 맞는 공모전이 아예 없음)
  카드 없이 기존 안내 문구만 발행한다.
  **(2026-08-05 갱신)** 추천 알고리즘을 규칙기반으로 확정: "카테고리 내 마감이 가장 많이
  남은 순서대로 최소 1~최대 3개" — 팀이 막 꾸려진 시점이라 준비 기간이 넉넉한 공모전을
  우선 보여주는 게 낫다는 판단. 조회 쿼리를 `findAllWithFilterAndDeadlineAsc`(마감임박순)에서
  `findAllWithFilterAndDeadlineDesc`(마감이 많이 남은 순)로 교체했고, `MockAiClient.recommendContests`는
  더 이상 셔플하지 않고 입력 순서(=이미 마감 내림차순으로 정렬된 상태)를 그대로 유지한 채
  상위 3개만 자른다.
- **공모전 투표 동률은 대상 아님**: 04-contest-voting.md에서 이미 "AI 추천 수락 경로 없음, 재투표만"으로
  확정했으므로 그대로 유지. `ContestVotingService.resolveDeadlineIfDue`의 "투표 참여자 0명" 무작위
  선택도 Phase 7에서 이미 구현된 그대로 유지 — AI 추천으로 교체하는 건 이번 스코프에 포함하지 않음
  (실제 LLM이 붙기 전까지는 무작위 선택과 실질적 차이가 없어서 우선순위를 낮춤).
- **`@챗봇` 자유 질의 (역할 분담/타임라인 추천 등)**: [requirements.md](../requirements.md)
  "챗봇 요구사항 2번"에 처음부터 있었지만 어느 Phase 계획에도 실제 구현 태스크로 잡힌 적이
  없어 빠져 있었다(구현 현황 확인 중 발견, 2026-07-30). `IN_PROGRESS_PROMPT` 안내 문구에만
  존재하고 실제 동작하는 로직은 없던 상태였는데, 이번에 뒤늦게 연결했다. 채팅 메시지가
  `"@챗봇"`으로 시작하면 자유 질의로 간주해 `AiClient.answerTeamQuestion`으로 답변을 받아
  챗봇 메시지로 발행한다. `Team.chatbotEnabled`가 꺼져있으면 응답하지 않는다(기존 챗봇
  on/off 토글을 그대로 존중). 특정 `TeamStatus`로 제한하지 않고 어느 단계에서든 멘션하면
  응답한다 — 요구사항 원문이 단계 제한 없이 "말 걸기 가능"이라고만 돼 있었기 때문.

## 실제 LLM 연동 (2026-08-05)

- **`answerTeamQuestion`만 실제 LLM으로 교체.** 나머지(팀장 후보/동률 추천, 공모전 추천)는
  PM이 정리한 규칙기반 점수 알고리즘이 이미 확정돼 있어 그대로 유지 — `generateSummary`/
  `evaluateProject`(AI 요약 기능)도 이번 스코프 밖(다른 기능이라 별도 논의 필요).
- **프로바이더: Google Gemini(`gemini-2.5-flash-lite`)** — 결제수단 등록 없이 API 키 발급만으로
  쓸 수 있는 무료 티어라 학생 프로젝트 규모의 저빈도 호출(팀당 가끔 `@챗봇` 멘션)에 적합하다고
  판단해 선택. OpenAI/Anthropic은 신규 가입 시 소액 체험 크레딧만 주고 이후 결제수단 등록이
  필요해 이번엔 채택하지 않음.
- `global/ai/GeminiClient.java` 신규 — Gemini REST API(`generateContent`) 호출 전담,
  Spring `RestClient` 사용(새 의존성 불필요). `GEMINI_API_KEY`(`application.yml`
  `ai.gemini.api-key`, 기본값 빈 문자열)가 비어있으면 `isEnabled()`가 false를 반환한다.
- `MockAiClient.answerTeamQuestion`이 `GeminiClient`를 주입받아, 활성화돼 있으면
  Gemini를 호출하고 결과를 그대로 반환한다. **키가 없거나(로컬/테스트) API 호출이 실패하면
  기존 키워드 기반(역할/타임라인) 응답으로 폴백** — 이 프로젝트 대부분의 다른 기능처럼 개발
  환경에서 외부 의존성 없이 돌아가야 한다는 원칙을 지켰다.
- 클래스 이름은 `MockAiClient`로 그대로 유지했다 — 다른 메서드(팀장/공모전 추천)는 여전히
  규칙기반이라 "Mock"이 여전히 맞고, `AiClient` 구현체를 하나 더 늘려 빈 등록을 애매하게
  만들기보다(다른 서비스들이 전부 `AiClient` 하나만 주입받는 구조) 기존 빈 안에서 분기하는
  쪽이 변경 범위가 훨씬 작았다.
- 테스트: `MockAiClientAnswerTeamQuestionTest`(Gemini 성공/실패 폴백/비활성/빈 질문 4케이스,
  `GeminiClient`를 Mockito로 목킹). 기존 `MockAiClientTest`(규칙기반 알고리즘 검증)는
  생성자에 비활성 `GeminiClient`를 넘기도록만 수정.

## AI 호출 비동기 분리 (2026-08-15, 스레드풀 점유 이슈 점검)

`AiGatewayClient`의 타임아웃이 연결/응답 각각 20초라, AI 호출이 걸린 두 지점이 그만큼 DB
트랜잭션이나 스레드를 오래 붙잡고 있었다.

- `ChatbotOrchestrationService.advanceToContestSelecting`이 `@Transactional` 안에서
  `AiClient.recommendContests`를 동기 호출 — 팀장 선출 마감 스케줄러(`resolveLeaderSelectionDeadlines`)
  가 마감 지난 팀을 순차 처리하다 그중 한 팀에서 AI 응답을 기다리는 동안 DB 커넥션과 스케줄러
  스레드를 계속 붙잡는 구조였다([07-scheduler.md](./07-scheduler.md) 참고).
- `advanceAfterGreeting`의 OPEN_NOMINATION 분기(`postLeaderNominationCard`)도 `@Transactional`
  안에서 `AiClient.recommendLeaderCandidates`를 동기 호출 — 인사 유도 타임아웃
  스케줄러(`forceAdvanceGreetings`)가 여러 팀을 순차 처리할 때 동일한 문제가 있었다.
- `respondToMentionIfAny`도 `@Transactional` 안에서 `AiClient.answerTeamQuestion`을 동기
  호출 — 웹소켓(STOMP) 메시지 처리 스레드가 AI 응답을 기다리는 동안 막혀서, 같은 시간대 다른
  채팅방의 메시지 전송까지 지연될 수 있었다.

기존 프로젝트 AI 요약 기능(`ProjectAiSummaryService`)이 쓰던
`TransactionSynchronizationManager.registerSynchronization(...).afterCommit()` +
`@Async("aiSummaryExecutor")` 패턴(`ProfileService`에서 재요약 트리거 시 사용)을 그대로
재사용해 두 흐름을 쪼갰다.

- **공모전 추천**: `advanceToContestSelecting`은 이제 `Team.status` 전이와 마감 세팅만 동기로
  커밋한다. 커밋 이후에만 신규 `ChatbotContestRecommendationAsyncService.recommendContestsAsync`
  가 `aiSummaryExecutor`에서 AI를 호출하고, 결과는 신규 `ChatbotContestRecommendationTxService`
  가 새 트랜잭션에서 반영한다(추천 있으면 후보 등록 + `CONTEST_RECOMMEND_CARD` 발행, 없으면
  일반 안내 문구만). `ContestCandidate` 등록 로직(팀장으로 등록자 채우기, 중복 스킵)이 이
  TxService로 그대로 옮겨졌다 — [04-contest-voting.md](./04-contest-voting.md)의 "AI 추천
  공모전이 실제 후보로 등록되지 않던 문제" 항목 참고.
- **`@챗봇` 자유 질의**: `respondToMentionIfAny`는 멘션 여부/`chatbotEnabled` 확인만 하고(쓰기가
  없어 `@Transactional`도 제거), AI 호출은 신규 `ChatbotMentionAsyncService.answerMentionAsync`
  로 위임한다.
- **팀장 후보 추천(OPEN_NOMINATION)**: `advanceAfterGreeting`은 `Team.status` 전이(→
  `LEADER_SELECTING`)와 마감 세팅만 동기로 커밋한다. 커밋 이후에만 신규
  `ChatbotLeaderNominationAsyncService.recommendLeaderNomineesAsync`가 `aiSummaryExecutor`
  에서 AI를 호출하고, 결과(추천 이름 포함 문구 + `LEADER_NOMINATION_CARD` 발행)는 신규
  `ChatbotLeaderNominationTxService`가 새 트랜잭션에서 반영한다. 공모전 추천과 다르게 카드
  타입이 항상 하나(`LEADER_NOMINATION_CARD`)뿐이라, AI 호출이 실패해도 "추천 없음"과 동일하게
  처리해 같은 카드를 발행한다(별도 폴백 문구 불필요).
- **(2026-08-15 추가 발견) 팀장 투표 동률 추천**: 후보 등록/투표 마감 분리 작업 리뷰 중, 위
  세 곳을 고칠 때 놓쳤던 네 번째 동기 호출을 발견했다 — `LeaderElectionService.tally()`가
  동률을 감지하면 `@Transactional`(`castVote`) 안에서 `AiClient.recommendTiebreakLeader`를
  동기 호출하고 있었다. 이 트랜잭션은 유저의 투표 요청(`castVote`)뿐 아니라 팀장 투표 마감
  스케줄러(`resolveVoteDeadlineIfDue`)에서도 열릴 수 있어 동일한 문제였고, 라운드마다 독립된
  8시간 마감을 받게 되면서 2라운드(동률 재투표)가 스케줄러 마감까지 살아남는 경우가 훨씬
  흔해져 실제로 부딪힐 가능성도 커졌다. `tally()`는 동률 판정까지만 동기로 하고, AI 호출/이후
  처리(재투표 카드 재발행 또는 2라운드+ 자동 확정)는 커밋 이후 신규
  `LeaderTiebreakAsyncService`/`LeaderTiebreakTxService`가 이어받는다.
- AI 호출이 예외를 던지면(타임아웃 등) 네 서비스 모두 예외를 삼키고 폴백한다 — 공모전 추천은
  일반 안내 문구로, 팀장 후보 추천은 "추천 없음"과 동일한 카드로, 멘션 응답은 그냥 메시지를
  남기지 않는 것으로, 팀장 투표 동률 추천은 AI 추천 없이 재투표 카드를 발행하는 것으로(기존
  동작과 동일 — 추천 실패와 "동률 후보 중 추천 대상이 없음"을 구분하지 않는다).
- 스레드풀 제출 자체가 실패하는 경우(`TaskRejectedException`, 풀 포화)는 각 서비스가 잡아서
  로그만 남기고 넘어간다 — `ProfileService`의 기존 AI 요약 트리거와 동일한 처리 방식. 공모전
  추천/팀장 후보 추천 둘 다 같은 `afterCommit` 등록 보일러플레이트를 쓰므로
  `ChatbotOrchestrationService`에 `runAfterCommit(...)` private 헬퍼로 묶었다 —
  `LeaderElectionService`는 별도 클래스라 이 헬퍼를 공유하지 않고 동일한 블록을 인라인으로
  그대로 둔다(`ProfileService`가 애초에 이 패턴을 헬퍼 없이 인라인으로 썼던 것과 동일).
- 테스트: `ChatbotOrchestrationServiceTest`/`LeaderElectionServiceTest`는 이제 "커밋 전엔
  비동기 서비스가 호출되지 않고, 커밋 후에만 올바른 인자로 위임되는지"만 검증한다
  (`ProfileServiceTest`와 동일하게 `TransactionSynchronizationManager.initSynchronization()`/
  `afterCommit()` 수동 트리거 패턴 사용). 실제 AI 응답 처리/후보 등록/중복 스킵/AI 예외 폴백/
  라운드별 확정 분기 등 세부 로직 검증은 `ChatbotContestRecommendationAsyncServiceTest`/
  `TxServiceTest`, `ChatbotLeaderNominationAsyncServiceTest`/`TxServiceTest`,
  `ChatbotMentionAsyncServiceTest`, `LeaderTiebreakAsyncServiceTest`/`TxServiceTest`로
  옮겼다.

- `generateSummary`/`evaluateProject`(AI 요약 기능)의 실제 LLM 연동은 여전히 스코프 밖 —
